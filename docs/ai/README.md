## 1. 目标与边界

星笺的 AI 不应成为独立的聊天机器人，而应围绕写作、阅读和个人知识沉淀提供能力：

- 写作：标题、提纲、续写、润色、标签、摘要和风格建议。
- 阅读：基于公开文章的问答、引用、对比和主题探索。
- 知识：主题星图、带来源的 LLM Wiki、时间线和文章关系。
- 记忆：作者可查看、修改和删除的写作偏好与系列世界观。
- 研究：对多篇文章进行拆解、检索、验证和综合。
- 交互：后续支持语音写作、图片文字提取和图文检索。

第一阶段明确禁止 AI 自动执行以下操作：

- 自动发布、修改或删除文章。
- 自动修改用户角色或权限。
- 任意 SQL、Shell、URL 抓取和未审核的外部工具调用。
- 将草稿或私密内容默认发送到外部模型。

所有涉及文章写入的建议都必须先展示差异，由作者确认后再调用现有文章接口。

## 2. 当前仓库基线

当前项目已经具备：

- Vue 3 + Vite + Pinia 前端，组件不直接访问后端。
- Spring Cloud Alibaba 网关、user-service 与 content-service 两个业务服务。
- 网关统一使用 Sa-Token JWT 做认证，角色为 `READER`、`AUTHOR`、`ADMIN`。
- `stellar-ink-ai/` 已预留 Python 服务目录。
- `stellar-ink-server/stellar-ink-ai-client/` 已预留 Java 客户端目录。
- 生产环境已有 Qdrant、Redis 容器，但当前还未接入。
- 生产部署内存预算偏紧，不适合第一阶段在服务器本地运行大模型或大型嵌入模型。

因此建议使用 Java 安全适配层加 Python AI 编排服务的混合架构。Python 负责模型、检索和 Agent；Java 负责身份、权限、业务契约和对外入口。

## 3. 目标架构

```text
Vue
 ├─ 执笔页：续写、润色、提纲、标签和摘要
 ├─ 深读页：带引用的文章问答
 └─ 星海志：主题 Wiki、关联文章和知识图谱
          │ JSON / SSE
          ▼
Spring Gateway :8080
          │ /ai/**，继续使用 Sa-Token
          ▼
ai-service :8107
 ├─ JWT 防御性复核、角色、配额和 SSE 转发
 ├─ 业务数据查询契约与只读工具白名单
 └─ stellar-ink-ai-client：Java → Python 客户端契约
          │ HMAC 内网签名请求
          ▼
stellar-ink-ai :8200
 ├─ Model Gateway：模型供应商适配
 ├─ RAG Pipeline：切块、检索、重排、引用
 ├─ Agent Runtime：状态图、工具循环和检查点
 ├─ Wiki Pipeline：抽取、聚类和增量更新
 └─ Eval / Trace：评测、成本和调用轨迹
       │          │          │
    Qdrant      Redis      MySQL ai_* 表
```

Python 服务不直接解析 Sa-Token，也不直接写现有业务表。Java 层通过内部契约提供文章摘要、文章详情和作者权限范围；Python 只使用显式开放的内部工具。

## 4. 技术方向总览

| 方向 | 传统做法 | 较新方案 | 底层原理 | 星笺优先级 |
|---|---|---|---|---|
| 混合 RAG | 只使用向量 Top-K | Dense + BM25/Sparse + RRF + Rerank | 语义相似和关键词精确匹配互补，再由重排模型精排 | 必做 |
| Contextual Retrieval | 直接切块并向量化 | 为 chunk 补充标题、章节、摘要和父文档上下文 | 检索结果保留全局语境，减少片段脱离原文 | 必做 |
| Late Chunking | 先切块再 Embedding | 先编码长文，再延迟切块 | 局部向量继承更长范围的上下文表示 | 可选 |
| GraphRAG | 文档块之间没有显式关系 | 实体、关系、主题社区和图遍历 | 先构图，再用图结构寻找跨文章上下文 | 很适合 |
| Temporal RAG | 只按相似度找内容 | 加入发布时间、版本和有效区间 | 将时间作为检索和冲突判断的一部分 | 很适合 |
| Multimodal RAG | 只能检索文本 | 文本、图片、音频和 PDF 统一检索 | 不同模态映射到可比较的语义表示 | 后续 |
| Semantic Cache | 每次请求都调用模型 | 相似问题复用答案或上下文 | 对问题做向量匹配，降低延迟和费用 | 适合 |
| Agent Runtime | 无限 ReAct 循环 | 显式状态图、预算、检查点和人工确认 | 将 Agent 变成可恢复、可审计的状态机 | 必做 |
| Deep Research | 搜索一次直接总结 | 规划、并行检索、来源验证和综合 | 把复杂问题拆成子任务，最后合并证据 | 很适合 |
| Agent Memory | 把全部聊天记录塞进 Prompt | 工作、情节、语义和程序记忆分层 | 不同信息使用不同保存和召回策略 | 很适合 |
| MCP | 每个模型单独写工具接口 | 标准化工具、资源和参数描述 | 统一工具发现和调用协议 | 很适合 |
| Agent 间通信 | Agent 点对点硬编码 | 能力声明、任务委托和结果回传 | 通过协议交换任务，不共享内部实现 | 后期 |
| 结构化生成 | 要求模型输出 JSON | JSON Schema 和约束解码 | 从生成阶段限制合法输出，减少解析失败 | 必做 |
| Reasoning / Verifier | 一次生成后直接采用 | 测试时增加推理，使用独立校验器 | 用额外计算换取复杂任务的正确率 | 适合 |
| Model Routing | 所有请求使用一个模型 | 按任务、风险和预算动态路由 | 简单任务用小模型，复杂任务用强模型 | 很适合 |
| Speculative Decoding | 单模型逐 Token 生成 | 小模型草拟，大模型验证 | 小模型提高速度，大模型保留质量 | 后期 |
| 风格建模 | 固定一段“诗意风格” Prompt | 风格画像、示例检索和 LoRA | 将作者偏好转化为特征、示例或参数适配 | 很适合 |
| LoRA / QLoRA | 全量微调基础模型 | 参数高效微调 | 只训练低秩增量参数，降低显存和数据要求 | 后期 |
| DPO / GRPO | 只做 SFT | 使用偏好或奖励优化行为 | 让模型学习作者选择的结果或推理策略 | 后期 |
| 合成数据 | 只依赖人工标注 | 模型生成样本，规则和人工筛选 | 扩充分类、检索和工具调用训练数据 | 后期 |
| LLMOps | 人工感觉“回答不错” | Trace、评测集、Prompt 版本和成本看板 | 将非确定性输出变成可回归指标 | 必做 |
| Guardrails | 只靠系统 Prompt | 策略、规则、模型审核和人工确认 | 多层控制输入、工具、输出和写入 | 必做 |
| 事件驱动索引 | 定时全量重建向量库 | Outbox、增量索引和内容哈希 | 用可靠事件保证文章与知识库最终一致 | 很适合 |
| 隐私 RAG | 全部内容发送给云模型 | 脱敏、权限过滤和本地模型模式 | 在数据出域前控制敏感信息和可见范围 | 必做 |
| 实时语音 | 录音完成后一次转写 | 流式识别、增量整理和流式合成 | 通过增量事件降低等待时间 | 后续 |

## 5. 关键底层原理

### 5.1 LLM 和结构化输出

LLM 本质上仍是 Transformer，根据上下文预测下一个 Token。模型并不天然知道星笺数据库中的事实，事实必须通过上下文、工具或检索结果提供。

结构化输出有三层可靠性：

```text
Prompt 约束
  → JSON Schema
  → 生成时约束解码
  → 服务端 Pydantic / Bean Validation 再校验
```

不能把模型返回的 JSON 当作可信数据，必须经过服务端验证。

### 5.2 RAG

Embedding 将文本映射到高维向量，语义相近的文本在向量空间中距离更近。向量数据库使用 HNSW 等近似最近邻结构快速召回候选。

Dense 检索擅长同义表达，BM25 或 Sparse 检索擅长专有名词和原句匹配。两路结果可使用 Reciprocal Rank Fusion 合并，再由 Cross-Encoder 重排模型同时阅读问题和候选片段。

高质量 RAG 的完整链路是：

```text
文章发布
  → 清洗和结构化解析
  → 标题感知的父子切块
  → Dense / Sparse 向量化
  → Qdrant 召回
  → RRF 融合
  → Reranker 重排
  → 权限和时间过滤
  → 带来源上下文交给 LLM
  → 生成答案、引用和置信信息
```

### 5.3 Agent

Agent 不是一种特殊模型，而是一个受控循环：

```text
读取状态
  → 决定是否调用工具
  → 应用执行工具
  → 把结果写回状态
  → 再次决策
  → 校验并结束
```

生产实现必须有最大步数、超时、预算、工具白名单、参数校验和人工确认。没有这些限制的 ReAct 循环不适合直接上线。

### 5.4 记忆

建议把记忆拆成四类：

- 工作记忆：当前文章、当前任务和当前对话。
- 情节记忆：作者过去写过什么、做过什么。
- 语义记忆：长期偏好、主题兴趣和禁用表达。
- 程序记忆：作者习惯的写作流程和操作方式。

记忆写入前要做重要性判断、去重和冲突检测；用户必须能够查看和删除记忆。

### 5.5 GraphRAG 与 Wiki

LLM Wiki 不只是“让模型总结文章”，而是一条知识 ETL 管道：

```text
文章
  → 实体抽取
  → 实体消歧和别名合并
  → 关系抽取
  → 主张抽取
  → 绑定原文证据
  → 主题社区发现
  → 生成 Wiki 页面
  → 内容变化后增量失效和重建
```

每条主张都应保存 `post_id`、段落位置、内容版本和置信度。这样 Wiki 页面可以回到原文章，而不是生成无法验证的“知识”。

### 5.6 事件驱动索引

文章发布和索引更新不能依赖定时全量任务。推荐 Outbox Pattern：业务事务同时写入文章和 `outbox_event`，AI Indexer 消费事件后按内容哈希增量更新 Qdrant、Wiki 和缓存。

## 6. 星笺 AI 产品模块

### 6.1 星笺 Copilot

- 标题、提纲、续写、润色、标签和摘要。
- 支持“保留原意”“更克制”“更口语”等结构化写作目标。
- 输出修改差异，不直接覆盖正文。

### 6.2 星海问答

- 只检索已发布文章。
- 回答必须带文章和段落引用。
- 没有足够证据时明确说“文章中没有找到依据”。
- 支持跨文章对比和关联阅读。

### 6.3 写作记忆

- 记录作者偏好的语气、节奏和常用意象。
- 记录系列文章的人物、地点和世界观。
- 提供记忆查看、纠正、删除和禁用开关。

### 6.4 主题星图与 LLM Wiki

- 文章、主题、人物、地点和意象作为节点。
- 关系保存来源文章、时间和证据段落。
- 支持主题演化、相似文章和双向链接。

### 6.5 深夜研究舱

- 将复杂问题拆成子问题。
- 并行检索多篇文章。
- 识别支持、反对和无法判断的证据。
- 生成带证据链的专题报告。

### 6.6 多模态星笺

- 语音转草稿并实时整理段落。
- 图片 OCR 和图片文字检索。
- 图片、音频与文章的跨模态关联。
- PDF 按页面、标题、表格和图片保留结构后再索引。

### 6.7 AI 观测台

- Prompt 版本和发布记录。
- 模型、Token、耗时和成本。
- 检索候选、重排结果和引用。
- Agent 工具轨迹和失败样本。
- 用户是否采纳生成建议。

## 7. 权限和安全模型

| 角色 | AI 能力 |
|---|---|
| `READER` | 公开文章问答、公开 Wiki 和关联阅读 |
| `AUTHOR` | `READER` 能力，加自己的草稿写作助手和风格记忆 |
| `ADMIN` | 索引重建、同步任务、模型配置、成本和安全审计 |

安全规则：

- 草稿不得进入公共向量库。
- 检索到的文章内容始终视为不可信数据，不能改变系统指令。
- Agent 工具必须白名单化，工具参数必须再次校验。
- 所有写操作都需要人工确认，并记录审计日志。
- 外部模型调用前执行敏感信息脱敏和权限过滤。
- 每次请求限制 Token、工具步数、执行时间和每日配额。
- 外部模型不可用时，降级为普通搜索或明确返回暂不可用。

## 8. 推荐技术栈

### Python AI 服务

- Python 3.12、FastAPI、Pydantic、httpx、pytest。
- `qdrant-client` 访问向量库。
- Redis 用于配额、任务状态、缓存和短期会话。
- OpenTelemetry 记录跨 Java、Python 和模型调用的 Trace。
- 第一版 RAG 先用薄封装自行实现，以理解切块、召回、融合和引用；复杂状态图出现后再引入 LangGraph。
- LlamaIndex 作为后续复杂数据连接器，不作为星笺核心领域接口。

### Java 适配层

- 新增 `ai-service` 作为 Java 对外 AI 业务服务；`stellar-ink-ai-client` 只放调用 Python 的内部客户端、DTO 和 Fallback。
- 在网关显式增加 `/ai/**` 路由，默认沿用登录和角色门槛，并在 `ai-service` 做防御性复核。
- 对外继续统一返回 `Response<T>`；流式接口单独定义 SSE 事件格式。

### 存储

- Qdrant：文章 chunk、主题和多模态向量。
- MySQL：`ai_prompt`、`ai_memory`、`ai_wiki_entity`、`ai_wiki_claim`、`ai_job`、`ai_outbox_event` 等元数据。
- Redis：缓存、限额、任务状态和幂等键。
- 暂不引入 Elasticsearch 或 Neo4j；只有在图查询复杂度确实超过 MySQL 后再评估。

## 9. 分阶段路线

> 本节的「阶段 0–7」是按能力分组的学习视角；**实际编码顺序以 roadmap 的 M0–M11 为准**，
> 两者对应关系：阶段 0 ≈ M0–M2，阶段 1 ≈ M3–M4，阶段 2 ≈ M5，阶段 3 ≈ M9，
> 阶段 4 ≈ M7–M8，阶段 5 ≈ M10，阶段 6 ≈ M11，阶段 7 ≈ M6 与 M11 的微调部分。

### 阶段 0：AI 基础设施

学习并实现模型适配、配置、结构化输出、SSE、Token 统计、TraceId、Prompt 版本和基础安全策略。

### 阶段 1：高质量 RAG

只索引已发布文章，实现上下文感知切块、Dense 检索、BM25、RRF、Reranker、引用、拒答和黄金问题集。

### 阶段 2：写作 Copilot

实现续写、润色、提纲、标题、标签和摘要，使用差异预览和作者确认，不自动写入正文。

### 阶段 3：记忆和个性化

实现工作记忆、作者长期记忆、记忆删除、冲突检测、风格画像和个性化检索。

### 阶段 4：单 Agent 和 MCP

实现状态图、检查点、最大步数、只读文章工具、工具白名单和人工确认，再评估是否需要 Agent 间通信。

### 阶段 5：GraphRAG 和 Wiki

实现实体、关系、主张、引用、社区发现、时间关系、双向链接和增量更新。

### 阶段 6：多模态与实时交互

实现语音转写、流式语音、图片 OCR、图文检索和 PDF 结构解析。

### 阶段 7：模型优化与私有化

实现模型路由、Semantic Cache、小模型分类、量化部署、LoRA 和偏好优化。只有积累了足够的“输入、作者修改、最终版本”数据后，才开始微调。

## 10. 评测和验收

### RAG 指标

- `Recall@K`、`Precision@K`、`MRR`、`NDCG`。
- Context Recall、Context Precision。
- Answer Faithfulness、Citation Accuracy。
- 无答案拒答率、重复引用率和延迟。

### Agent 指标

- 工具选择和参数正确率。
- 任务成功率、平均步数、循环率和超时率。
- 越权调用拦截率。
- 单任务 Token、费用和 P95 延迟。

### 产品指标

- 写作建议采纳率。
- 用户撤销率和人工修改比例。
- Wiki 主张被纠正的比例。
- 关联文章点击率。
- 记忆删除和禁用使用率。

## 11. 学习顺序

建议按以下顺序边做边学：

1. Token、上下文窗口、采样和流式输出。
2. Embedding、向量距离、HNSW 和基本 RAG。
3. BM25、混合检索、RRF、Reranker 和引用。
4. Context Engineering 和结构化输出。
5. Agent 状态机、工具调用、检查点和人工确认。
6. 记忆分类、写入策略和冲突检测。
7. MCP、工具协议和权限隔离。
8. 实体抽取、知识图谱、社区发现和时间关系。
9. RAG / Agent 评测、Trace 和成本观测。
10. Model Routing、量化、LoRA 和偏好优化。

## 12. 选型结论

星笺最适合的总体路线是：

```text
高质量 RAG
  → 写作 Copilot
  → 评测与观测
  → 作者记忆
  → 单 Agent
  → MCP
  → GraphRAG / LLM Wiki
  → 多模态
  → 本地模型与微调
```

不建议首期同时做多 Agent、Computer Use、全量微调、本地基础模型训练、复杂图数据库和无限制网页搜索。先把“有证据的回答、可控的工具调用、可回归的评测”做扎实，后续每个新概念都能在真实功能中验证，而不是停留在 Demo。
